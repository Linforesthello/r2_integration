## 主题 G：闸门类工具的误报治理（未抽取，全文保留；09-16 新增）

> 来源事件：[2026-09-16 校验器代码跨度修复](retrospect/2026-09-16_checker_codespan_fix.md)（缺失 14 → 0，其中 12 条为假报）。
> 候选去向：[doc-engineering.md §四](doc-engineering.md)（校验器规则）/ [§九](doc-engineering.md)（一致性体检）邻域，成熟后抽。

### G1 闸门类工具变更须双验证：合成自测 + 集合比对

- **规则**：改动验收闸门（校验器/检查脚本）后，除"全仓跑通数"外还须两层对照——
  ① **合成自测**：临时造正反例（真坏链必报 / 示例不报）证明新逻辑双向正确；
  ② **集合比对**：**内容固定、只换脚本**，对新旧「参与校验集合」求差——**新增 = 0 才算未削弱**，减少项逐组核过
- **案例**：新校验器全仓 947 校验 / 0 缺失；集合比对新增 0 条、减少 13 组 = 12 假报示例 + 2 条「代码区内但可解析」的引用

### G2 误报治理：改工具，不改规范示例

- **规则**：示例假报的根因在工具（解析器不懂"代码跨度内非链接"语义），修工具；
  规范里的教学示例**一字不动**（守 §四「格式示例 → 不动」）
- **案例**：12 条假报全位于行内代码/围栏内，置空代码跨度后消失；standards §1.5 示例原样保留

### G3 「基线」是危险词

- **规则**：长期固定的缺失数会掩盖「其中大部分是工具误报」——周期性回看基线**构成**，不只看数字
- **案例**：「缺失恒为 14 = 既有基线（格式示例 + 历史坏链）」被放行多轮，实为 12/14 假报

### G4 同文件内并发 WIP：逐路径 `git add` 隔离不到行级

- **规则**：用户 WIP 隔离按**文件**路径做，隔离不到**行**——用户并发编辑同一文件时，`git add <file>` 会连带其改动入提交。
  对策：提交前 `git diff --cached <file>` 逐行核；必要时按 hunk `git apply --cached` 只 stage 自己的块；
  与用户约定并发会话避开同一文件
- **案例**：09-16 `b2caad1` 带入用户并发新增的 README 树行（该行目标文件仍未跟踪）——泄漏已报告，处置待用户定

### G5 闸门口径留档法

- **规则**：改动闸门后同时记录「旧口径 / 新口径 / 跳过数」并说明差值构成，防口径漂移与二次困惑
- **案例**：旧 961 校验/12 缺失 → 新 947 校验/跳过 16/0 缺失

## 主题 H：镜像同步的中间态识别（未抽取，全文保留；09-16 新增）

> 来源事件：2026-09-16 装法定档批次镜像同步（权威源 r2_integration `c6a9853`/`cc25e4e` ↔ 镜像 `06fae45`）。
> 候选去向：[obsidian-sync.md §4](obsidian-sync.md)（镜像独有/旧快照处理）邻域，成熟后抽。

### H1 并行会话期，镜像可能捕获权威源文件的「中间态」

- **判据**（三条同时成立 = 中间态旧副本，**不是**「镜像独有」）：
  ① 权威源存在同名文件；
  ② 镜像 mtime 落在权威源该次修改**之前**（本次：权威源终版 13:22，镜像捕获于 12:48）；
  ③ diff 内容 = 权威源早期形态的**子集**（本次 101 行，全为用户补充信息前的旧表述）
- **处置**：按 [obsidian-sync §4 第 2 条「过时旧快照」](obsidian-sync.md)直接单向覆盖，
  **不进入「镜像独有」调查流程**（§4 第 1~3 步）；同步后 `diff -rq` 归零即闭环
- **反例（不该做的）**：把中间态当「镜像独有」去权威源他处找重命名迁移，或当作用户手工改动而保留——
  两者都会把中间态留在镜像，破坏「镜像 = 权威源副本」不变量

### H2 镜像同步范围须含仓根 README——勿只同步 `doc/`

- **规则**：镜像根（`R2_Integration/`）对应**仓库根**，其中 `README.md` 属同步范围；只同步 `doc/` 会让仓根
  README 长期停留旧版，镜像不再是"权威源的完整副本"
- **案例**：2026-09-16 核对逐文件改动量时发现——镜像 `README.md` 单次同步即产生 **184 行 diff**
  （权威源本批仅改 2 行），即历次镜像同步均未覆盖仓根 README，漂移累积多日
- **自检口径**：同步后跑**全量** `diff -rq <仓根> <镜像根>`（而非只跑 `doc/`），排除构建产物 / bag 等
  不入镜像目录；残留项逐条归因，不得以"doc/ 已 0 差异"当作整体同步完成

## 主题 I：不入 git 内容的删改纪律与恢复（未抽取，全文保留；09-16 新增）

> 来源事件：2026-09-16 raw 底稿处置（`raw_经验盘点A1_候选汇总_2026-09-09_1342.md` 删除后用户决定保留 → 由会话记录恢复）。
> 候选去向：[doc-engineering.md §八](doc-engineering.md)（数据资产/破坏性操作）或 §七（协作边界）邻域，成熟后抽。

### I1 不入 git 的底稿：删除前先确认可恢复性，误删后从会话记录恢复

- **风险认知**：`raw_data/` 类底稿**不在 git**——`rm` 即永久丢失（无版本可回退），
  与仓库内文件（`git checkout --` 可救）**风险等级完全不同**；处置前应显式确认
- **误删恢复法（本次实证：295 行全文恢复，特征逐项吻合）**：
  ① 定位会话记录——`grep -rl "<底稿关键词>" ~/.claude/projects/<项目哈希>/*.jsonl`；
  ② **优先取该文件的 Read 工具结果**（`tool_result`）——它含**整篇内容且带 `cat -n` 行号**；
     取**最后一次 Read**（须在最后一次 Edit 之后）= 终态全文；比"Write + 多轮 Edit 重放"更省事且不易错；
  ③ 剥离 `^\s*\d+\t` 行号前缀还原；④ 用**已知特征核对**（行数 / 条目数 / 章节数，本次 295 行 / 126 条 / 7 批）
- **采信判据**：同一会话对该文件**多次 Read 且长度一致** → 期间无改动，可采信该快照
- **纪律建议**：处置"删除不可逆"类文件前，先确认可恢复性（会话记录 / 他处副本 / 先拷入 git 跟踪位）

## 主题 J：新传感器驱动接入（vendor / 运行态 / 串口 / 显示）（未抽取，全文保留；11-06 新增）

> 来源事件：[2026-11-06 LD06 VM 接入与冒烟](retrospect/2026-11-06_ld06_vm_bringup_smoke.md)。
> 候选去向：[ros2-ops.md §2](ros2-ops.md)（构建/部署）、[§7](ros2-ops.md)（排障）、[§7.1](ros2-ops.md)（无真车验证）邻域，成熟后抽。

### J1 第三方 ROS2 包 vendor 入仓：去内层 `.git` + 来源卡 + 包根平铺

- **规则**：从外部工作区把驱动包装进主仓时，用 `rsync -a --exclude='.git' --exclude=build --exclude=install --exclude=log`；
  入仓后 `test -d <pkg>/.git` 必须为假。带内层 `.git` 会被外层 git 记成 gitlink，GitHub 只显示目录、不展开源码。
  包放在仓根（与其它 `package.xml` 包平级），包内写 `README_R2.md` 记录上游仓库/commit/版本/License/本地改动。
- **验证**：`colcon build --packages-select <pkg>`；运行态用 `ps` 看进程可执行文件路径是否在新 install。
- **案例**：LD06 包 31 文件/276K，去 `.git` 后正常入仓；`README_R2.md` 记上游 `bf668a8` 与端口改动。

### J2 新传感器驱动冒烟：进程路径 + 频率 + 单发布者 + frame + TF + 短窗

- **规则**：冒烟 PASS 的六项最小判据——① 进程可执行文件在目标 install；② 数据源成功日志；③ 话题频率与手册量级一致；
  ④ 单发布者；⑤ `frame_id` 正确；⑥ TF 可解析、短窗无 timeout/退出。**冒烟 PASS ≠ 验收 PASS**：
  精度、安装方向、长跑、目标机、下游算法必须单列“未覆盖”。
- **运行态判据**：`ros2 pkg prefix` 受 shell 的 `AMENT_PREFIX_PATH` 顺序影响，不能单独作为“跑的是哪份包”的证据；
  以进程命令行/可执行文件路径为准。
- **案例**：LD06 冒烟 `/scan` 9.996–10.001 Hz、单发布者、`base_laser`、TF z=0.18；
  同一 shell 未 source r2 时 `pkg prefix` 命中外部 workspace，source 后命中 r2，但进程路径始终在 r2。

### J3 串口传感器掉电/接触判定：`Actual BaudRate` ≠ 数据流

- **规则**：串口能打开、`Actual BaudRate reported` 打印成功，只证明 tty 配置成功，**不证明传感器在发数据**。
  判定顺序：本体 LED/转动 → 连续 timeout 日志（约 100 ms 一条）→ 重启后 3 s 内有无有效帧 →
  重插供电是否恢复 → 再查带载电压/接头/共地/5V 来源。
- **案例**：LD06 首跑 18m36s 后蓝灯灭/停转；重启打印 230400 但 3 s 无帧 → `communication is abnormal`（exit 1）；
  重插后恢复。判为供电/接触瞬断，未改驱动。

### J4 包内 RViz 配置造成的“180°/变色”是显示差异

- **规则**：先比 `Fixed Frame`、颜色变换器、点大小/样式、保存的相机位姿，再怀疑数据；
  相机 `Yaw≈180°` 只转视角，不转 `/scan`。方向验证用已知非对称场景或 `angle_min/angle_max + ranges`。
- **案例**：`ldlidar.rviz` 的 `Yaw=3.1354`（179.6°）+ Intensity 彩虹（22–245）+ Flat Squares 3px；
  TF 旋转为单位四元数，`laser_scan_dir=True`，数据方向未被反转。

## 主题 K：LaserScan 规格/裁剪实测与一次性探针工具（未抽取，全文保留；11-07 新增）

> 候选去向：[ros2-ops.md §5.1](ros2-ops.md)（scan 数值分析）/ [§7](ros2-ops.md)（排障）/ [§10](ros2-ops.md)（进程卫生）邻域，成熟后抽。
> 说明：单事件新经验，按四层制先落 draft，不直写规则层。

### K1 一次性订阅探针：别在回调里 shutdown，用硬退出 + SIGKILL 兜底

- **规则**：抓 N 帧就退的 rclpy 探针，用 `spin_once(timeout_sec=...)` 轮询 + 每行 `flush=True`；
  抓够后 `os._exit(0)` 硬退出。**不要**在订阅回调里调 `rclpy.shutdown()`。
- **原因**：Humble 单线程 executor 下回调内 shutdown 会死锁（实测进程睡眠、无任何输出）；rclpy 初始化时
  安装了 SIGINT/SIGTERM handler，外部 `timeout` 的 SIGTERM 只触发"优雅关闭"、杀不死进程（实测卡 100s+）。
- **清理**：外层用 `timeout -k 5 30 python3 ...` 做 SIGKILL 兜底；`ros2 run` 是 wrapper + 子进程两段，
  按精确模式（bracket 防自杀匹配）或分别按 PID 清理，结束后 `ps` 复核。
- **案例**：2026-11-07 首版探针在回调里 shutdown → 卡死 100s+，`kill -TERM` 无效、只能 `kill -9`；
  改 `spin_once` + `os._exit` 后两轮实测均退出码 0。工具入仓 [scripts/probe_laserscan.py](../scripts/probe_laserscan.py)。

### K2 传感器规格：消息字段/驱动常量 ≠ 实测值，逐帧变化量单列

- **规则**：回答"波束数/角分辨率/量程"时先分三层——① 消息字段/驱动常量（如 `range_max=25.0`）；
  ② 驱动按数据反推的派生量（如 `angle_increment=2π/(beam_size−1)`，逐帧变）；
  ③ 实测观测量（本圈点数、有效回波最大距离、帧间隔）。只把 ③ 与可核实的 ① 写成结论，② 标"派生/逐帧变"。
- **判据**：`len(ranges)` 与 `angle_increment` 必须多帧采样看一致性；只抓 1 帧会把逐帧变化误当固定值。
- **案例**：LD06 三帧 `len(ranges)=455/452/454`、`angle_increment=0.7930/0.7982/0.7947°`；
  `range_max=25.0` 是驱动常量；室内有效回波最大 6.08 m（不当作量程结论）。

### K3 angle crop 的坐标约定要用非对称带实测钉死

- **规则**：驱动裁剪参数若按原始角计算、输出又做了方向反转，裁剪带在发布侧会镜像；
  **对称带会掩盖两种约定**，必须用非对称带（如 `[0,90]`）实测一次，才能钉死映射。
- **案例**：LD06 `crop[135,225] → 发布角[134.3,225.7]`（对称，无法区分）；`crop[0,90] → 发布角[269.4,360.8]`
  ⇒ 发布角 = 360° − 原始角。换算：掩盖发布角 `[α1,α2]` 设 crop `[360−α2, 360−α1]`。
- **附带事实**：crop 只把值置 NaN，消息长度与 `angle_min/angle_max` 不变，下游按"无回波"处理。

## 主题 L：网络可达性分层诊断与"假故障"复盘（未抽取，全文保留；11-07 新增）

> 来源事件：2026-11-07 VM/N97 双机网络诊断（explore_lite 取包"阻塞"复核）。
> 数据落档 `doc/raw_data/raw_netdiag_2026-11-07_1210.txt`（VM，含第 6 段补测）、
> `raw_netdiag_n97_2026-11-07_1215.txt`（N97）（本地，不入 git）。
> 规则层候选去向：[ros2-ops.md §1](ros2-ops.md)（多机环境）/ [§7](ros2-ops.md)（排障纪律）邻域，成熟后抽。
> 说明：单事件新经验，按四层制先落 draft，不直写规则层。

### L1 分层诊断顺序：路由 → DNS → ICMP → TCP → TLS/HTTP → 应用（git）

- **规则**：判断"外网不通"按六层顺序跑，每层只回答一个问题、逐层排除；不要在应用层（git/浏览器）反复试错。
- **各层判据**：

| 层 | 检查 | 结论 |
|:---|:---|:---|
| 路由 | `ip route \| grep '^default'` | 无 default = 网关丢失，与目标站无关 |
| DNS | `getent hosts <域名>` | 解析失败 = DNS 不转发外网 |
| ICMP | `ping` 国内公共 DNS + 目标 | 只作辅证（部分网络禁 ping） |
| TCP | `timeout 8 bash -c 'cat </dev/null >/dev/tcp/<host>/443'` | 免装 nc；不通 = 端口级阻断 |
| TLS/HTTP | `curl -w 'http=%{http_code} dns=… conn=… tls=… total=…'` | conn 有值而 tls 空 / total 超时 = TLS/SNI 层被干扰 |
| 应用 | `GIT_CURL_VERBOSE=1 timeout 30 git ls-remote <url>` | 日志停在 `Trying IP:443…` = 卡在 TCP；输出 refs = 全链路通 |

- **国内基线对照必做**：同时测 2 个国内站点（baidu/gitee）。国内通 + 目标不通 = 定向阻断；全不通 = 本机没出网。
  没有对照就无法区分这两类，容易把"定向阻断"误判成"整网故障"。

### L2 代理 TUN / fake-ip 指纹：别把本地回环当真实连通

- **指纹**：`ip addr` 出现 `Meta` / `tun*` / `utun*` 虚拟网卡（常见 `198.18.0.1/30`），
  且域名解析到 `198.18.x.x`（`198.18.0.0/15` = TUN 模式 fake-ip 池）→ 本机代理接管流量。
- **陷阱**：此时 `ping <域名>` 的 RTT 可能是**亚毫秒（实测 0.15~0.25ms）**——那是 TUN 网卡本地应答，
  **不是真实网络 RTT**，不能用来证明"外网很快"。连通性判据只认 `curl` 的 `http_code` 与 git 的 exit code。
- **反向用法**：同一台机"时通时不通"、解析 IP 在真实地址与 `198.18.x.x` 之间切换 → 是代理开关变了，不是链路抖动。

### L3 控制变量对照：同一台机、同一时段、多次运行，只改一个变量

- **规则**：怀疑"环境问题"时，在同一台机短时间内重复采集，把唯一变化量单独摘出来做对照表。
  比跨机比对可靠——跨机会混入两台机的配置差异。
- **案例**：VM 三次 run 中 `ens33` / `ens37` / 默认路由 / DNS / proxy 变量全程不变，唯一差异是 `Meta` 接口；
  github 解析随之在 `20.205.243.166`（真实）↔ `198.18.0.4`（fake-ip）切换，git 由 exit=124 ↔ exit=0。
- **附带纪律**：多行诊断脚本粘贴到终端可能**丢换行**（表现为 `curl: (6) Could not resolve host: echo`、
  `tail: 无法以读模式打开 'echo'`）→ 远程指导优先给**单行**命令，或让用户落成脚本再执行。

### L4 "原因未定位"的阻塞要标明生效条件，避免沉淀成假故障

- **规则**：把某事项记为"阻塞"前先问「这是持续故障，还是某个操作前提没满足？」——
  依赖代理 / 特定网络环境 / 某服务在线的事项，应记为**操作前提**（附验证方法），不写成故障。
- **代价**：本项目"explore_lite 源码构建受网络阻塞（原因未定位）"被写进 4 份状态文档，
  实际根因只是代理没开；后续每次交接都会被当成真实障碍重复排查。
- **纠正动作**：状态文档保留旧表述并划删除线 → 紧跟实测结论与前提条件（翻案留痕，见
  [doc-engineering §十](doc-engineering.md)）；不静默改写旧句。

### L5 代理环境下 GitHub 推送：SSH 22 不通改 SSH over 443

- **症状**：`git push` 报
  `kex_exchange_identification: Connection closed by remote host` /
  `Connection closed by 198.18.0.4 port 22`。解析到 `198.18.x.x` 说明流量走代理，
  **代理通常不放行 22 端口**——这不是密钥/权限问题，`https://github.com` 与 `ssh -p 443` 都正常。
- **判据**：`ssh -T -p 443 git@ssh.github.com` 认证通过，而默认 22 端口的 `git push` 失败
  → 结论是端口级阻断，**不要去重配 SSH key**（2026-11-07 首轮排障方向就是错的）。
- **一次性做法（不改全局配置，推荐）**：

  ```bash
  git -C <repo> -c url."ssh://git@ssh.github.com:443/".insteadOf="git@github.com:" push origin main
  ```

  `insteadOf` 只改写本次命令的 URL，仓库 `remote.origin.url` 保持原样。
- **永久做法（属全局配置变更，需用户确认后再做）**：`~/.ssh/config` 增加

  ```text
  Host github.com
    HostName ssh.github.com
    Port 443
    User git
  ```

- **案例**：2026-11-07 双仓推送，Obsidian 镜像与 r2_integration 均报同一错误；
  改 443 后两仓一次推成功，远端 HEAD 与本地一致。
- **配套工具**：网络层诊断用 [scripts/net_diag.sh](../scripts/net_diag.sh)（只读、单文件、两机通用）。

## 主题 M：假阴性归因——「观测工具 / 观测时机 / 事实」三分法（未抽取，全文保留；11-07 新增）

> 来源：[retrospect 2026-11-07 explore P1](retrospect/2026-11-07_explore_p1_param_declaration.md)。
> 与 ros2-ops §5「空结果先自查观测/记录链」互补：那条覆盖**工具侧**，本主题补**时机侧**。

### M1 三分法：先怀疑时机，再怀疑工具，最后才认事实

| 归因层 | 含义 | 典型症状 | 既往案例 |
|:---|:---|:---|:---|
| 观测工具侧 | 工具自身限制或判据写错 | `hz` 对大消息"一直等"；`max()` 遇 nan 静默漏报；记录器崩 | ros2-qos-dds §三、ros2-ops §5.1 |
| **观测时机侧** | **被观测对象尚未进入"能回答"的状态** | `param list` 只显示部分参数；`node list` 有节点但服务不响应 | **本例** |
| 事实侧 | 确实不存在 / 确实没发生 | 源码也没有、行为侧也复现不出 | — |

判据顺序：先查"对象此刻走到哪了"（日志停在哪个等待点）→ 再查工具 → 最后才接受"事实不存在"。

### M2 构造期阻塞：声明代码没跑到 ≠ 参数不存在

- C++ 成员初始化列表**先于构造函数体**执行。若成员对象的构造函数含无超时等待循环，
  构造函数体（常放 `declare_parameter`）永远不执行。
- 判别信号：`param list` 只出现"更早声明的那一批"，且数量恰好等于某个成员类的声明集。
- 排查：读初始化列表 → 找该成员构造函数里的 `while/wait_for_` → 逐层伪造依赖解锁。
- 本例三段阻塞：costmap 首帧 → `map→base_link` TF → `/navigate_to_pose` action server。

### M3 同进程 A/B 对照（比跨进程对比硬）

同一个进程内先取基线 A，注入一个变量后取 B；A→B 跳变即因果。跨进程/跨次对比会被
环境变量、overlay、daemon、残留进程污染。

### M4 伪造依赖件解锁（ROS2 三件套）

`ros2 topic pub -r 1` / `static_transform_publisher` / `python3 -c` 内联 `ActionServer`。
纪律：临时进程、按 PID kill、`ps -p` 复核。

### M5 `ros2 topic pub --once` 的 DDS 发现竞态

volatile QoS 下，`--once` 在 discovery 完成前发完即丢；对已在等待的订阅者要 `-r 1` 连续发。
（与 ros2-qos-dds §一 的 QoS 兼容矩阵同源，但这是**时序**问题，不是 QoS 不兼容。）

### M6 复测方案要先评审"能否证伪"

若无论真相如何都得到同一结果，那只是重放而非复测。先补能产生分叉的条件再跑。
