# 文档标准

> 维护者：所有写文档的人
> 适用范围：通用准则适用于任何项目，项目专用准则仅用于 `r2_integration/`

---

## 第一部分：通用文档准则

### 1.1 单一事实来源

**一条信息只在一个地方维护**，其他地方通过引用指向它。

| 信息类型 | 唯一存放位置 | 其他地方该怎么做 |
|:---------|:-------------|:----------------|
| 目录结构/文件树 | `README.md` | `见 README.md`，不复制树 |
| 技术参数 | 最相关的配置/代码文件 | 引用该文件路径，不复制数值 |
| 进度状态 | `02-progress.md` | 阶段性文档写"详见 02-progress.md" |
| 踩坑记录 | 各自的 `debug_log.md` | 不要在不同文件里重复记同一个坑 |

**反对**：在 `debug_log.md` 里放完整文件树（前车之鉴 ✅ 已修正）

---

### 1.2 按职责分文件，不按序号堆叠

用 **有意义的文件名** 代替序号，避免 `08.md`、`09.md` 这种无信息量的命名。

| 类型 | 推荐 | 不推荐 |
|:-----|:------|:--------|
| 全局总纲 | `plan.md` | `01-plan.md`（前缀编号在需要显式阅读顺序时可用） |
| 技术参考 | `chassis_definition.md` | `04-misc.md` |
| 完成报告 | `completion_report.md` | `done.md` |

**序号前缀只在需要规定阅读顺序时使用**，且仅用于 `doc/` 顶层的全局文档
（`01-plan.md` → `02-progress.md` → `03-current_state.md` → `07-handover.md`）；
`phaseN/`、`retrospect/` 内的文档不用序号（事件记录用日期前缀）。

---

### 1.3 全局 vs 局部分离

将文档分为两类，放在不同层级：

```
docs/
├── global/              ← 跨阶段、跨模块的文档
│   ├── plan.md
│   └── architecture.md
│
└── module-name/         ← 只属于某个模块/阶段的文档
    ├── spec.md
    └── debug_log.md
```

- **全局文档**：项目计划、整体进度、架构总览、交接文档
- **局部文档**：某个阶段的完成报告、某个驱动的调试日志、某项测试的记录

**局部文档不得包含全局文件树**，最多列一个「相关文件」短清单。

---

### 1.4 文件命名规范

| 规则 | 说明 | 示例 |
|:-----|:------|:------|
| 小写 + kebab-case | 单词间用连字符 | `ekf-config.md` ✅ `EKF_Config.md` ❌ |
| 扩展名 `.md` | 纯 Markdown | ✅ |
| 名称即内容 | 不看内容能猜出文档主题 | `debug_log.md` ✅ `stuff.md` ❌ |
| 避免序号为主 | 序号可作前缀，不作标识 | `01-plan.md`（可接受）`plan.md`（更优）|

---

### 1.5 交叉引用规范

```
引用同一仓库的文件：  [显示文本](path/to/file.md)
引用代码行：          [file.py:42](src/file.py#L42)
引用外部文档：        [标题](URL)
引用同一个文件内部：  [跳转标题](#标题名)
```

**规则**：
- 仓库内引用始终用**相对路径**（`doc/plan.md` 而非 `/home/user/docs/plan.md`）
- 跨机器部署/命令示例可用 `~/`（如 `~/Lin_workspace/r2_integration/...`），这是唯一允许的绝对形态
- 跨文档引用时标注简要说明：`[EKF 配置](phase1/ekf-config.md) — 融合参数详解`
- Obsidian 双向链接（`[[...]]`）仅用于个人笔记，**不在项目文档中使用**

---

### 1.6 Markdown 格式规范

| 要素 | 规范 |
|:-----|:------|
| 标题层级 | `#` 文档标题，`##` 一级分区，`###` 二级分区，不超过 `####` |
| 代码块 | 始终标注语言 ` ```python `、` ```yaml `、` ```bash ` |
| 表格 | 表头用 `|:---` 对齐，数据对齐 |
| 任务列表 | `- [x]` 已完成，`- [ ]` 未完成，`- [/]` 部分完成 |
| 强调 | **粗体** 用于关键术语，`行内代码` 用于文件名/命令/变量名 |
| 分隔线 | `---` 仅在章节间使用，不在节内滥用 |

---

### 1.7 维护契约

修改文档结构（增删文件、路径变更）后，必须执行：

```bash
# 1. 更新 README.md 的文件树
# 2. 检查所有交叉引用是否失效
grep -rn "已废弃文件名\|旧路径" --include="*.md" .

# 3. 更新进度文档
# 4. 通知协作成员
```

### 1.8 AI 辅助改文档的约束（2026-07-31 教训）

**教训来源**：2026-07-31 校对修复 01-plan.md 时，AI 未经核实就编造了
KISS-ICP 安装路径、启动命令等细节，与实际记录不符，需返工。

**规则**：

1. **必须指定唯一事实来源**：让 AI 改文档前，明确指定"以哪个文件为准"
   （如 `retrospect/vlp16_slam_exploration.md`、`config/r2_params.yaml`、实际代码文件），
   并要求所有改动内容都能从该来源核实
2. **禁止编造细节**：路径、命令、参数、话题名、状态等，来源里没有的
   一律不写，或标注"（待核实）"让真人确认
3. **先读再改**：AI 必须实际读取来源文件后再动手，不允许凭记忆/推测
4. **残留检查**：改完后 grep 旧关键词确认无残留（见 1.7 第 2 步）
5. **大改分批审**：超过 20 处的批量修改，先给改动清单让真人过目再落地

### 1.9 Obsidian 标签规范

Obsidian 库（`~/Lin_note/Open-Notes-Library/`）的笔记用行内分层标签（`#顶层/二级/...`）。
**给 Obsidian 镜像/笔记打标签前先读 [obsidian-tags.md](obsidian-tags.md)**：

- 顶层分类只复用不新建，叶子层可扩展
- 已解决问题用 `#Problems/solving/...`，未解决用 `#Problems/unsolved/...`
- 镜像侧 = 权威源内容 + 标签增强，标签只加在 Obsidian 镜像侧

### 1.10 Git 提交规范

**提交信息 = 标题 + 描述体（body）**。标题一行，描述体在空行后，
用来说明"改了什么、为什么、有什么影响"——让 `git log` 就能回溯，不用翻文档。

**标题格式（必填）**：`模块|主题`，一行

| 要素 | 规则 | 示例 |
|:-----|:-----|:-----|
| 模块 | R2 / Arm / MCLM / Syc / Note 等（首字母大写） | `R2|` |
| 主题 | 一句话说清"改了什么"，≤50 字 | `G354轴映射与两处符号修正` |

**描述体（推荐；多文件/修复类必填）**：空行后写三部分，用 bullet 列表：

```
R2|G354轴映射与两处符号修正，传感器安装定义留档

- 改动: imu_node.py +mount_axes 轴映射; init/Mahony 两处符号修正; 新增 sensor-mount.md
- 原因: G354 出厂轴定义(z下)与驱动假设不符, 两处符号 bug 被 z 朝下双负抵消掩盖
- 影响/注意: 启动须带 mount_axes:=y_front_x_left_z_down; 关联 retrospect/2026-08-02_ekf_tf_fusion_fix.md
```

**规则**：

1. **阶段完成即提交**（修复验证通过 / 文档更新完就 commit），不留积压——
   避免"发现没同步才一步更新"的被动提交
2. **排障/修复类提交**：body 必须关联排障文档（`retrospect/YYYY-MM-DD_*.md`）
3. **build/install/log/*.bag 不入库**（`.gitignore` 已配置，提交前 `git status` 确认无意外文件）
4. **多机器同步**：VM 提交推送 → N97 `git pull`（不再 scp 拷贝代码）
5. **Co-Authored-By**：AI 辅助的提交**默认不加** `Co-Authored-By` 标记，
   仅在显式要求时添加（如"本次提交带 Co-Authored-By"）。原因：该标记会把
   AI 计入 GitHub 贡献者列表，署名与否应由提交者本人决定

### 1.11 调研/选型文档必须附"来源"小节（2026-08-23 用户要求）

调研类文档（选型对比、方案决策、技术探索结论）的结论**必须有来源可回查**，
防止"看着像结论、实际是 AI 编的"。参考范式：[planning-control-roadmap.md §5.9](roadmaps/planning-control-roadmap.md)（2026-09-03 归入 `roadmaps/`）。

| 要素 | 要求 | 示例 |
|:---|:---|:---|
| 小节标题 | `来源（YYYY-MM-DD 核实方式）` | `### 5.9 来源（2026-08-23 WebSearch 核实）` |
| 链接保留 | 每条结论可溯源到官方仓库/文档/论文/社区帖，**必须用 markdown 链接**，不复制成纯文本 | `[m-explore-ros2 仓库](https://github.com/robo-friends/m-explore-ros2)` |
| 核实标注 | 文档头部标注核实途径与未实测项 | `> 来源 = 官方仓库/README + WebSearch 社区核实，未实测项标注` |
| 回查口径 | 结论行内可附来源编号/链接，面试或交接时能按链接回查 | `TEB 在 Humble 处于弃养（[讨论帖](...)）` |

**规则**：

1. **调研结论 ≠ 事实**：未实测、未落地、仅"社区如此说"的结论必须标注（`未实测` / `待验证` / `社区方案`），不得写成已验证
2. **来源优先官方**：官方仓库/文档 > 社区论坛 > 个人博客（与全局"官方路径优先"一致）
3. **链接防失效**：链接标题用仓库名/论文名（人可搜索），不只写 URL 裸文本
4. **与 1.8 衔接**：AI 写调研文档时，每条结论对应至少一个来源链接；来源无法核实的结论不写，或标"（待核实）"

> **执行案例与重申清单**：2026-08-23 对 roadmap 全篇真实性回溯的完整过程、关键决策（不编造链接/官方优先/实测与规格分离）与可复用检查清单，见
> [retrospect/2026-08-23_doc_source_traceback.md](retrospect/2026-08-23_doc_source_traceback.md)——后续写/改调研文档时按该清单重申

### 1.12 编辑纪律：只增不删（2026-08-25 定）

**修改全局/规范类文档（CLAUDE.md、standards.md 等）时，一般情况只增不删**：
新增内容直接加；删除或改写既有内容前，必须先向用户确认。

- 适用范围：全局规则、文档规范等长期有效文档；普通工作文档按正常流程改
- 理由：既有内容（含具体示例、历史结论）是上下文与可追溯依据，删改后难以复原；
  增补优于替换——需要通用写法时，保留原文另加一般性写法
- 教训（2026-08-25）：通用化改写 CLAUDE.md「原始数据留存」落盘位置时直接删掉原示例，
  被用户叫停「不要删」——应保留原文，新增一般性写法

### 1.13 检索与调研留档规范（2026-09-05 定）

**检索纪律**（行为层，与全局 CLAUDE.md「信息检索」条配合）：需要外部检索（web search 类）时，
先询问用户是否优先检索**本地已存档知识库**（locowiki `~/locowiki_ws`、Obsidian 个人库
`~/Lin_note/Open-Notes-Library`、项目 doc/retrospect、doc/surveys 等）——本地权威源优先，
足以定论即不再外搜；本地无果或需官方一手来源才 WebSearch/WebFetch。

**每次 Web 检索（WebSearch/WebFetch）结果必须本地留档**，按用途分两档：

| 档位 | 适用 | 落位 | 要求 |
|:---|:---|:---|:---|
| 正式档 | 服务于调研/选型/方案决策，结论需长期查证 | 随项目 doc 树，正式文档、可提交；R2 = `doc/surveys/`（2026-09-05 建） | §1.11 全部要素：头部标注检索途径与「未实测」项，逐条结论配 markdown 来源链接；未实测不得写成已验证 |
| 轻量档 | 单点临时检索，不足以成文 | `<项目根>/doc/raw_data/raw_websearch_<话题>_<YYYY-MM-DD>_<HHMM>.md`（不入 git） | 文件头：检索词/问题、日期时间、来源=WebSearch/WebFetch；内容 = 一句话结论 + 用到的 URL 清单 |

**规则**：

1. 正式档命名用主题名（如 `3d-lidar-2d-navigation-survey.md`），日期写头部、不用前缀（§1.2）
2. 轻量档定位 = 事后回查/防重复外搜；结论沉淀后应升格并入正式档，不留孤儿文件
3. 来源优先级与链接防失效口径同 §1.11：官方 > 社区 > 个人博客；链接标题用仓库/文章名
4. 已落正式档的检索不另存轻量档（§1.1 单一事实来源，同一内容不重复存）

> 执行案例：2026-09-05 低矮障碍感知调研 → `doc/surveys/3d-lidar-2d-navigation-survey.md`
> （头部核实途径 + 全部手段标未实测 + 全站链接可回查），检索流水内含其中，未另开轻量档

### 2.3 Phase 文档规范

每个 `phaseN/` 目录包含该阶段的全套文档，遵循以下约定：

**必须有的文件**（视阶段需要）：

| 文件 | 内容 | 示例 |
|:-----|:------|:------|
| `plan.md` | 该阶段的详细实施步骤 | Phase 1 的 EKF 配置步骤 |
| `completion_report.md` | 本阶段完成时写，记录成果和遗留问题 | Phase 0 完成报告 |
| `debug_log.md` | 该阶段遇到的坑和解决过程 | 方向标定的 8 组测试记录 |
| `test_report.md` | 测试方法、数据、结论 | EKF 融合 vs 纯轮速对比 |

**Phase 文档的引用规范**：
- 只列本阶段「相关文件」短清单，**不列全局文件树**
- 引用全局文档用相对路径 `[进度总览](../02-progress.md)`
- 引用代码用相对路径 `[chassis_node.py](../../r2_bringup/r2_bringup/chassis_node.py)`

**内容包含**：
- 前置依赖（哪个 Phase 的前置条件）
- 本阶段的输入/输出
- 关键配置和参数
- 验证方法
- 遗留问题 / 待办

---

### 2.4 ROS2 包文档规范

ROS2 包本身的标准文件（`package.xml`、`README.md` 等）由 ROS2 规范约束。此外：

- 每个包的 `README.md` 简要说明包的用途、话题、参数
- 包的配置文件（`config/*.yaml`）要加注释说明每个字段的含义
- 不属于某个 ROS2 包的共享文档（如标定记录）放在 `doc/` 对应 Phase 下

### 2.5 文件树放置规则（R2 专用）

| 文件位置 | 能否有文件树 | 理由 |
|:---------|:-----------:|:------|
| `README.md` | ✅ 必须有 | 入口导航，唯一权威来源 |
| `doc/01-plan.md` | ✅ 可以有 | 总纲文档，需要上下文 |
| `doc/02-progress.md` | ❌ 不要有 | 进度看板，不需要文件树 |
| `doc/03-current_state.md` | ❌ 不要有 | 状态快照，关注内容而非结构 |
| `doc/07-handover.md` | ❌ 不要有 | 交接文档，关注状态而非结构 |
| `doc/phaseN/*.md` | ❌ 不要有 | 局部文档，最多列「相关文件」 |

### 2.7 反模式清单

以下做法在本项目中应当避免：

| 反模式 | 示例 | 正确做法 |
|:-------|:------|:---------|
| 局部文档里放完整树 | `debug_log.md` 里有 `r2_integration/` 的完整树 | 只列本阶段相关文件 |
| 序号爆炸 | `08-config-notes.md`、`09-test-data.md` | 归入对应 `phaseN/` |
| 跨文档复制参数 | 在多个文件里写 `ticks_per_rev: 4241` | 只维护 `r2_params.yaml`，文档引用它 |
| 乱放 ROS2 包 | `doc/phase1/g354_driver/` | 包放工区根目录，doc 放引用 |
| 路径写死 | `/home/lin/.../file.yaml` | 用 `~/` 或相对路径 |
| 记坑无结论 | 只写"调了一天没调通" | 写最终怎么解决的，或为什么放弃 |
| AI 编造细节 | 文档里出现来源文件没有的路径/命令/状态 | 以唯一事实来源为准（见 1.8），来源没有的不写 |
